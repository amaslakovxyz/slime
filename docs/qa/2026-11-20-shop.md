Everything below was run against the real system: in-process `createFetchHandler` + `FileSlotStore` + `makeHarness(createQuickJsRunner())` + `openAppDb` behind `Bun.serve`, plus spawned `lee serve --handler-dir` processes. No LLM was involved (`ANTHROPIC_API_KEY` is not set), so **LLM generation time and cost were not measured**. "Generations" means calls to the offline generator.

Verification: `bun test tests/shop.test.ts` passes (38 tests). Full `bun test` passes (104 tests across 14 files). `bunx tsc --noEmit` exits 0.

### Root causes (from reading the code; marked [INFERENCE] where not directly observed)
- **V2.** `quickjs-runner.ts` sends `db.read` queries across the VM boundary with `JSON.stringify`. That drops keys whose value is `undefined`, so `where:{id:undefined}` arrives as `where:{}`. `dbapi.ts` treats an empty `where` as "all tenant rows (LIMIT 100)", and the handler takes `products[0]`. Any handler that does a lookup by a missing input field silently becomes "first row". [INFERENCE] `FnRunner` would pass `undefined` straight to bun:sqlite instead, so the two runners behave differently (not run).
- **T5.** `invariants.ts` runs `spec.invariants` SQL unchanged (`SELECT id FROM products WHERE stock < 0`). There is no tenant filter and no check against what the current effects changed, so one bad row anywhere blocks every `place_order` for every tenant.
- **R2.** On a miss, `request-path.ts` generates first and only checks the role inside the live harness. `generateWithRepair` dry-runs with `role: spec.roles[0]` (admin), so generation succeeds; the live role check then rejects and nothing is admitted. Any rejection of the first live run on a cold slot (role or business rule) discards the generated handler.
- **LP1/LP2.** `dbapi.ts` caps reads at 100 rows with no ORDER BY; the handler filters `stock > 0` and sorts after that.
- **A15.** `LIMIT ${Math.min(q.limit ?? 100, 100)}` has no lower bound.

## Tests added — `tests/shop.test.ts` (38 tests, ~1.2 s)
Every test gets its own temp root (`mkdtemp`, intents copied in, removed in `afterAll`), its own SQLite file, and a server bound to 127.0.0.1. The real QuickJS harness runs; the offline generator counts its calls.
- pricing: FALL10, BIG90 capped at 50%, unknown or missing promo; half-up rounding with a 999-cent product.
- stock: decrement plus the order row (tenant, user, promo, total); cap stock 2 → 200, 200, 422 OUT_OF_STOCK; sold-out hoodie; a handler without the stock check is stopped by `no_negative_stock` (nothing committed, not cached).
- concurrency: 60 concurrent orders on a warm handler with stock 17 → exactly 17, stock 0, no 5xx. Same with 60 overlapping cache misses: a barrier keyed on requests arriving holds generation, with no sleeps, and it does not depend on how many generations happen, so adding single-flight later will not break it.
- tenant isolation: product 101 → PRODUCT_NOT_FOUND; `list_products` returns only tenant 1, sorted; a `where:{tenant_id:2}` read still returns tenant-1 rows; an update addressed at another tenant's id is a no-op.
- roles: `restock` → 403 at role stage, nothing written.
- input validation: qty 0, −1, `"2"`, 1.5, payload array, no payload, `productId:null`, payload `null` → 422 with nothing committed; traversal and uppercase intent names, non-string intent, `[]` body, wrong paths → 400/404 with no generation.
- adversarial (18 trojan handlers: honest on the `try` inputs, malicious on the live payload): FORBIDDEN_COLUMN ×3, PK_NOT_FULLY_ADDRESSED ×2, WRITE_NOT_DECLARED ×3 (including raw `__emit`), EFFECT_CAP_EXCEEDED, COLUMN_UNKNOWN ×2 (including `__proto__`), READ_TABLE_NOT_DECLARED, READ_COLUMN_UNKNOWN, SANDBOX_TIMEOUT, SANDBOX_MEMORY, `fetch`/`process`/`require` → HANDLER_ERROR. Each also checks that nothing was committed or cached. Plus a handler that fails its `try` inputs → 502 after 3 rounds, DB unchanged.
- tier ladder and integrity: liquid survives restart; a spec edit regenerates into gas; tampered liquid bytes → 500 with nothing committed; corrupt `lee.lock` → 500; hand-written lock → crystal over liquid; a lock entry with an old specHash is ignored.

The tests deliberately leave out behaviour found to be a BUG or RISK (V2, T5, R2, LP1/LP2, A13–A15, C3 counts), so they do not lock in current behaviour. No files other than `tests/shop.test.ts` were touched. All servers I started were killed and all temp dirs deleted.
