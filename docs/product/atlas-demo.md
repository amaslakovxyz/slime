* **Status:** Current. Live at <https://g2a4gnm6afgghto6jah6qdxrpu0ycxbq.lambda-url.eu-central-1.on.aws/> since 2026-11-22 (Lambda, [platform/infra/atlas](../../platform/infra/atlas/README.md)); open it on your phone. Code: `examples/customer-site`.
* **Audience:** hackathon visitors and judges. One page; read it in two minutes.
* **Deeper:** [atlas-demo-cheatsheet.md](atlas-demo-cheatsheet.md) (who does what, with diagrams), [customer-demo-use-cases.md](customer-demo-use-cases.md) (the three cases, the demo script, measured numbers).

## Atlas in one paragraph

Atlas is a made-up B2B SaaS that bills its customers monthly. Its Postgres has 4 plans,
200 accounts, subscriptions, invoices in EUR cents and usage events. Customer complaints
live in Notion. Finance, Customer Success and account managers each want a dashboard.
Atlas has no backend team to build one. Its coding agent (Claude Code) got the task
"build a customer console" and wrote **no SQL, no API endpoints and no data layer**:
one Slime request per dashboard panel, and a 69-line server that holds the key.

## What you see on the site

Three cards. Each one has a Run button, the answer as a table, a badge with the tier
that answered (Gas, Liquid or Crystal), timings, and "The code that answered": the SQL
the model wrote.

| Card | Who asks | What it answers | What it proves |
|---|---|---|---|
| Revenue by plan | Finance | MRR and active subscriptions per plan | Runs as a **Crystal**: frozen code on its own route and token, no model call. |
| Churn risk by country | Customer Success | Past-due accounts in a picked country, biggest debt first | One request covers every country. Changing the country reuses the same **Liquid** handler, so no new tokens are spent. |
| Customer 360 | Account managers | Paid revenue in a picked currency next to open negative Notion feedback | One request reads Postgres, Notion and an FX API. It runs on a **self-hosted** Slime, so it is shown live at the demo table, not on the public URL. |

## What Atlas needed

| Need | Atlas's answer | Effort |
|---|---|---|
| A database | Its existing Postgres and a read-only role (`slime_reader`) | One `CREATE ROLE` and the grants |
| A Slime endpoint | Created in the admin (`admin.amaslakov.com`): database URL in, endpoint URL and `slm_` key out | One form |
| The requests | `src/panels.mjs`: per panel an `intent` in plain English, the `input` names and the `output` shape | 46 lines, written by the agent |
| A place for the key | `src/app.mjs`: forwards a panel id and the picked values to Slime. The browser never sees a key or an intent. | 69 lines |
| Production hardening | Crystallize in the admin once a handler has 10 good runs; the panel switches to the Crystal route | One click and two env values |

Atlas did **not** need an ORM, migrations for the dashboard, an API spec, a model key in
its own code, or a deploy of new backend code per filter.

## Why it is real

- **What is made up:** the company name and its data (generated by
  [`examples/express/db/init.sql`](../../examples/express/db/init.sql)).
- **What is real:** the database (RDS Postgres `slime-test-db`, eu-central-1), the Slime
  Cloud runtime (AWS Lambda), the admin, the model calls, the review and the Crystal in S3.
- **Measured on 2026-11-22**, through this site against Slime Cloud:
  - Churn risk, first call (Gas): the model wrote the handler in 5.6 s. From the 4th call
    the reviewer approved it (Liquid): 6-8 ms in the engine, no model call.
  - Revenue by plan after Crystallize: 3.5-4 ms engine time per call, 4 rows that match
    the database.
  - On the public URL the same day: Crystal 4.9-5.8 ms and Liquid 5.7-7.9 ms in the
    engine, 28-93 ms round trip once warm.
  - Customer 360, self-hosted, with a live model call but Notion and the FX API
    **replayed from recorded responses**: first generation 14.4 s across three sources;
    later currencies answer in 115-180 ms with no new generation.
- **What you can check yourself:** open "The code that answered" and read the SQL. Pick
  DE in Churn risk: the answer is empty, which is correct, because the data has no
  past-due accounts there. Slime does not invent rows.
- **Safety you can see:** the role Slime uses cannot read `accounts.password_hash` and
  cannot write. The page cannot ask a new question: it only sends values from the
  dropdowns.

## The one-line pitch

"Atlas's agent described the data each panel needs. Slime wrote, reviewed and froze the
code that fetches it, inside the database's permissions."
