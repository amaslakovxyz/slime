Slime · research · Idea 1

Live prod rebuilding: Crystal as an evergreen backend copy

Can Slime sit next to a live production service at the load balancer, watch its requests and responses, and keep rebuilding the service through Gas → Liquid → Crystal, with production itself as the test oracle? This is the approach Anthropic used to move its Messages API from Python to Rust, taken one step further.

00Verdict

GO · NARROWED
Worth building, but only as a shadow verifier for read endpoints. It should not be a "copy of any backend" that serves traffic.
  • What carries over from Anthropic. The production service acts as the oracle. Diff records hold the shape of a difference, not its content. The work runs in three loops: inner, outer and memory. Slime already has two of the pieces: the gate in crystal/src/equivalence.ts and the writer/reviewer/merge-gate agent loop.
  • What does not carry over. Anthropic ported code it already had. A listener at the load balancer has no source code: it would have to infer the logic from examples. Matching all the traffic it has seen does not make it correct on traffic it has not seen. Anthropic's own numbers show this: the Rust port passed about 98% of its tests while only about 25% of production inputs matched.
  • Hard limits on scope. Read-only GET endpoints backed by a database. The copy never answers end users (O2). Recordings stay inside the client's own network (O5). Writes are deferred (O4).

01What Anthropic actually did

~70%less CPU per request on Rust
~20%lower median time to first token
98% vs ~25%tests passing vs production inputs matching (April)

Why tests weren't enough

  • ~700 integration tests ran the Python API inside the test process. Porting the tests along with the code weakened 100+ assertions.
  • 20 binary options already give over a million combinations. The real definition of correct is whatever production users rely on.
  • Parity was a moving target: the Python API kept shipping features during the migration.

Shadowing on production traffic

  • The model ran once, and its output was replayed to Rust. This handles nondeterminism, and a customer is never billed twice.
  • The two versions were compared at checkpoints (accept/reject → settings → prompt pieces) and had to match exactly. The first checkpoint that differed showed where the bug was.
  • A fingerprint (step, piece, first differing byte, both lengths) separated one bug from another without anyone reading user text.

Three verification loops

  • Grouping: every 10–30 minutes a script grouped the diff records by kind. A coordinator agent was alerted only for a new kind, and gave each new kind to its own worker agent plus a Slack thread.
  • Inner loop: a cloud sandbox with both codebases. A local input/output check took under a second. The agent wrote a request that reproduced the fingerprint, edited the Rust until the outputs matched, and added a test.
  • The seam between loops was human review. Example: an engineer rejected a web-search "fix" that copied tool text into files. The verifier rewards a match, not a good fix.
  • Outer loop: deploys with and without the fix, compared by how often the fingerprint appeared on shadowed traffic of the same kind.
  • Memory loop: reviewers' corrections became CLAUDE.md rules, tests, lints and a merge check ("a Python change needs a matching Rust change").

Example diff record, as the post shows it (made-up values):

step: build prompt ← where in the code piece: 2 ← where in the prompt first diff: byte 17 ← fingerprint python: 190 bytes ← fingerprint rust: 190 bytes ← fingerprint

02The key difference: porting vs inferring

Anthropic leaned on the generator–verifier gap: writing the Rust from known Python was cheap, and verifying it was the bottleneck. A listener at the load balancer reverses this. Generation turns into program synthesis from examples, which has many valid answers, and verification is only as good as what the observed traffic happens to cover.

03Mapping onto Slime ("Slime Mirror")

The three phases in mirror mode

Gas (today: model on a new request)

A new route template appears in the traffic. The generator gets the schema, the dictionary and K observed pairs, plus the route's source code in mode B, and writes SQL and a shape function. The result is never returned to a user; it only runs in the shadow.

Liquid (today: runs + review)

Promoted after N matches in a row on distinct inputs, a noise-classified diff of zero, and an approved review. A mismatch sends the handler back to Gas with the fingerprint as context.

Crystal (today: cases = Liquid reference)

The key change: the reference becomes the production response, not the Liquid output. The cases file holds (input, prod output, build id). "Evergreen" means the continuous shadow keeps checking the Crystal against new prod builds.

Reuse vs new work (checked against the repository)

REUSE
  • Generator, sandbox, read-only lint, row cap and timeouts (@slime-cloud/core)
  • The equivalence rules: floats to 9 significant digits, list order counts (crystal/src/equivalence.ts)
  • <key>.cases.json, slime-crystal pin/verify, cost ≤ 1.1× the reference
  • Agent loop: writer → gate → 3 reviewers → merge-gate.mjs (crystal/agents/, crystal/scripts/)
  • Provenance drift (schemaHash), which extends naturally to the upstream build id
NEW
  • A tee that captures the prod response (Istio mirroring discards responses, so it isn't enough)
  • Route templating and a request key without intent text (O7)
  • Cases with prod output as the oracle instead of the Liquid reference
  • A JSON diff, fingerprinting, and grouping by kind
  • A noise classifier (Diffy-style, field-level only)
  • Per-route match rate by build: the dashboard and the stopping criterion

05Adversarial review

Steelman: the idea at its strongest

Production is the most complete specification a service has. Slime already turns observations into verified code: it has the read-only sandbox, the equivalence gate and the agent loop with a merge gate. With a tee at the load balancer and production as the oracle, Slime gets an endless stream of test cases for free. Gas, Liquid and Crystal become a ladder of trust, from "matches sometimes" to "frozen and verified". That gives an evergreen, verified copy of the read side of the backend, a target for migration (for example to a cheaper runtime), and an automatically maintained regression corpus.

The objections were raised one at a time, strongest first. Each is stated, attacked, defended, and given a status. Click an objection to expand it.

O1The analogy breaks: Anthropic ported, and Slime would have to inferSURVIVED · PARTIAL

Attack. The method rested on the generator–verifier gap: generating from known source was cheap. At the load balancer there is no source, so generating means synthesizing from input/output pairs, and the problem is underdetermined. With 10 runs (CRYSTAL_MIN_RUNS), many different programs match. For example, ORDER BY created_at and ORDER BY id agree on every observed case until the first backfill. Anthropic had 98% of tests passing and ~25% of production inputs matching, and that was while porting known code.

Defense. Split it into two modes. Mode B (source-assisted): the client owns the service, so it gives Slime the repository. The generator ports the route handler (the Anthropic setting), and the traffic only verifies. Mode A (black-box): only for the narrow class of "a projection of SQL over a known schema", and the honest claim is parity on the observed distribution, never "a copy of the service".

Status: mode B answers it. In mode A the risk stays, and the pitch must not promise "copies any backend".

O2Authorization is invisible in input/output, so the copy becomes an IDOR generatorSURVIVED

Attack. GET /orders?user_id=42 returns only user 42's orders because middleware checked the JWT. The observed pairs never contain a refusal, so the synthesized SQL filters only by the parameter. If the copy ever serves traffic, any user_id returns someone else's data (an insecure direct object reference, IDOR). Tenant scoping, feature flags and time-dependent logic are invisible in the same way.

Defense. (1) The copy is shadow-only: it never answers a user, the Scientist rule. (2) The verified principal and tenant become an explicit input of the key, and the cases must include refusals (401/403/404). (3) Read with a database role that has row-level security per tenant.

Status: rule (1) closes it for v0. Any plan to serve traffic from the copy needs a separate security review.

O3Database state and replica lag produce false mismatches; there are no checkpointsANSWERED

Attack. The response depends on the input, the database state at time t, the clock, and calls to neighbouring services. The load balancer sees only the input and the response. Replaying a request later against a changed database gives a mismatch with no bug behind it. A shadow run on a replica reads with lag. And with only an end-to-end diff there is nothing to localize with: Anthropic's checkpoints have no equivalent here.

Defense. (1) Run the shadow at once against the same replica, and on a mismatch re-request the original once. This is safe for GET, and it is Diffy's primary/secondary idea: fields that differ between two prod responses are noise, only for those fields. (2) The checkpoints move to Slime's own side: are the SQL rows wrong, or the shape? Slime controls its handler's steps. (3) The fingerprint is route · JSON path · kind (missing/extra/type/value/order) · Δlen · build. (4) Later: capture the database reads Keploy-style for exact replay.

O4A "backend copy" without writes is not a backendDEFERRED

Attack. Most microservice traffic includes mutations. Slime is read-only by invariant, and shadowing writes either duplicates side effects or needs a database fork for every request.

Defense. v0 covers GET routes only. Later: compare the planned writes (the SQL the copy would run) with the writes the original actually made, from change data capture (CDC) or the Postgres log, without executing them. That needs its own design; the product frame already says writes have no rollback.

Status: parked. The claims must say "read-side copy".

O5Recording bodies breaks "Slime Cloud never stores rows"SURVIVED · NEEDS A DECISION

Attack. product_frame_v0_2.md: Slime Cloud never stores rows or content. The tee records production responses (personal data) and feeds them to the generator's prompt. Anthropic got around this with shape-only diffs, but it had source code; black-box synthesis needs the values.

Defense. Mirror runs self-hosted, inside the client's network (core is a library, and that path exists). Recordings and cases never leave it. Only shape-only fingerprints go up to Slime Cloud. The generator sees the schema, types and (in mode B) source code, plus examples redacted by a schema dictionary.

Status: the cloud variant cannot happen without breaking the invariant. Anton has to choose (see Decisions).

O6A simpler alternative: Keploy + Diffy + Claude Code gets 80% of the valueANSWERED · WITH A CAVEAT

Attack. Capturing traffic and turning it into tests is Keploy. Diffing is Diffy. Porting is Claude Code. Why build another tee?

Defense. Slime's unique part is not capture or diffing. It is the automatic ladder (Gas → Liquid → Crystal with a gate the agents cannot change) and the self-healing loop with a merge gate. Both already exist in the repository. The caveat: don't build the capture yourself. Take an Envoy tap, a small Node proxy for the demo, or Keploy.

O7Slime's key needs an intent, and REST traffic has noneANSWERED

Attack. Today the key is the normalized intent, the input names and the output shape. REST has a method, a path, query parameters and a body. Responses with optional fields would change the "output shape" and break the key.

Defense. intent := METHOD /route/{template}, plus the OpenAPI summary if there is one. Templating follows the usual rule: numbers, UUIDs and high-cardinality segments become {param}. Output := the union JSON Schema over the observed responses. The key is the route template, not the shape of each response. This needs a new key version, KEY_VERSION.

O8The long tail: rare routes and branches never reach NANSWERED

Attack. Error paths, empty results, the last page of pagination and admin-only parameters show up rarely or never. The Crystal is green on the 95% of traffic it saw and wrong on the rest. Production also weights bugs by frequency, as the Anthropic post notes.

Defense. Parity is a statistical metric per route (match rate over a window, split by build), as in Anthropic's daily chart, not a binary "Crystal = done". A route counts as covered only at ≥ X% matches over ≥ M distinct inputs. The inner loop generates its own requests for the boundary cases, from the schema and the source code.

O9"Evergreen" turns into an endless chase plus overfitted fixesANSWERED

Attack. Every prod deploy moves the target. Agents will patch outputs to make them match, like the web-search shortcut in the post, and the copy collects workarounds.

Defense. (1) The tee reads a build id from a response header, and match rates are counted per build. A spike after a deploy demotes the Crystal to Liquid as a fallback, and the reason is a deploy, not a bug. (2) A fix gets into the Crystal only through merge-gate.mjs and a human PR review, the seam between loops. (3) Memory loop: rejections become rules in crystal/agents/*.md. (4) The budget is capped: no more than K agent runs per fingerprint kind.

What would have to be true

  • The target routes are read-only and backed by one database whose schema Slime can see.
  • A response is a deterministic function of (input, principal, database snapshot) once noise fields are removed.
  • Authorization can be expressed as an input (the principal or tenant in the key).
  • There is enough traffic per route to reach M distinct inputs within the window.
  • The client allows a tee at the load balancer and lets Slime run inside its network.
  • For mode B, the client gives read access to the route's source code.

07Hackathon slice: what can be shown in 1–2 days

Demo script

  1. A small hand-written REST service (3–4 GET routes) over the demo database examples/express/db/init.sql. This is the "legacy prod".
  2. A Node tee proxy in front of it that captures (request, response, x-build-id) and passes them to Mirror.
  3. A load script. On screen, the match rate per route climbs from 0% to 100%, and the routes go Gas → Liquid → Crystal.
  4. "Prod deploys": one field changes format, for example cents → dollars. The fingerprint GET /orders/{id} · $.total · value · build 7 appears, the Crystal is demoted, the agent loop opens a PR, and after the merge the route is green again.

Success / kill criteria

  • Success: ≥ 3 of 4 routes reach Crystal with a ≥ 99% match rate on ≥ 200 distinct inputs. A new fingerprint after the "deploy" is caught within 1 minute.
  • Kill: mode A cannot get above 80% on even one route without the source code, so mode A is dead and only mode B is pitched.
  • Out of scope: writes, the cloud variant, Envoy/Kubernetes, serving traffic from the copy.

The pitch in one sentence

"Anthropic made production the verifier for a migration. We make that a product: Slime listens to your service and grows a verified copy of its read side, one route at a time, without touching production."

08Decisions for Anton

D1 · Mode

B (source-assisted) as the main mode, A as an experiment with a kill criterion. Recommended: B.

D2 · Where it runs

Self-hosted inside the client's network (keeps the "no rows" promise) vs the cloud (breaks it). Recommended: self-hosted.

D3 · End state

Shadow-only (verifier and regression corpus) vs a migration target with gradual cutover. Recommended: shadow-only for v0.
