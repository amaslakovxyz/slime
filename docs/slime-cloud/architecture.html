slimecloud

Admin + endpoint provisioner. A local Next.js admin where users sign up, create and reconfigure endpoints and watch usage by tier; a stream-driven worker that deploys one Lambda per endpoint on a shared Gas layer, with Liquid handlers in DynamoDB partitioned by endpoint.

02Endpoint lifecycle: create, reconfigure, delete

The admin only writes endpoint items (pending, updating, deleting) and secrets. The DynamoDB stream hands those items to slime-provisioner, which does all AWS work. Every "already exists" error counts as success, so a stream retry replays safely. While a status is pending|provisioning|updating|deleting, the endpoint page calls router.refresh() every 5 s (a revealed token stays visible).

Admin (synchronous, in the server action)

  1. A1
    Validate name (1–40 chars), provider claude|groq|offline, connector postgres (the only available entry of the connector registry) with its Connection URL (postgres:// or postgresql://).
  2. A2
    Generate endpointId = "ep-" + 5 random bytes hex and token "slm_" + 24 random bytes base64url.
  3. A3
    Store secrets /slime/endpoints/<id>/DATABASE_URL and /SLIME_API_KEY as SSM SecureString (locally: a 0600 git-ignored JSON file).
  4. A4
    PutItem the endpoint item with status = pending, connectorType = postgres and tokenHint (last 4 chars). If this fails, the secrets are removed again.
  5. →
    Stream record INSERT with NewImage.status = pending passes the event source filter and invokes the worker (batch size 1, 2 retries).

Provisioner · provision(ep)

  1. 1
    Claim: UpdateItem status = provisioning with ConditionExpression #s = :pending. A ConditionalCheckFailedException means another invocation owns it: stop.
  2. 2
    Log group /aws/lambda/slime-ep-<hex> (ignore ResourceAlreadyExistsException), then PutRetentionPolicy.
  3. 3
    Role slime-ep-<hex> with Lambda trust, PermissionsBoundary = slime-endpoint-boundary, tags Project=slime, Endpoint=<id>; then inline policy endpoint scoped to this endpoint (see §6).
  4. 4
    CreateFunction slime-ep-<hex>: shim zip + Gas layer, nodejs22.x, arm64, 1024 MB, 30 s, X-Ray active, JSON logs. Env: SLIME_SSM_PREFIX=/slime/shared/,/slime/endpoints/<id>/, SLIME_TENANT_ID, SLIME_HANDLERS_TABLE, SLIME_USAGE_TABLE, SLIME_PROVIDER, SLIME_CRYSTAL_DIR and SLIME_OFFLINE_FILE under /opt/slime. On "cannot be assumed" (IAM propagation) retry every 3 s, up to 20 times.
  5. 5
    Wait until the function is Active (waitUntilFunctionActiveV2, max 120 s).
  6. 6
    Function URL with AuthType NONE (on conflict: read the existing one), plus the two public permissions PublicFunctionUrl and PublicInvokeViaFunctionUrl, copied from runtime.tf.
  7. 7
    Health: read the token from SSM, GET <url>healthz with x-api-key. Up to 5 tries, 3 s apart, on 403 or 5xx (cold start, IAM, DB).
  8. 8
    Result: 200 → status = ready, url, layerArn, remove error. Otherwise → status = failed with the first 300 chars of the body. Any error in steps 2–7 also ends in failed and the batch succeeds, so the stream never blocks.

Reconfigure (updating) · admin, from the Connector and Settings tabs

  1. U1
    updateConnector: validate, check ownership with getEndpoint. pending → overwrite DATABASE_URL only (condition: still pending). ready|failed → read the old secret, overwrite it (SSM Overwrite: true), then conditional UpdateItem status = updating, connectorType, updatedAt (#s IN (:ready, :failed)). If that condition fails, the old secret is restored and the action throws NOT_UPDATABLE; any other status is NOT_UPDATABLE too.
  2. U2
    updateSettings: a name change is a plain update (any status except deleting); a provider change is allowed only from ready|failed and sets status = updating.
  3. →
    Stream record MODIFY with NewImage.status = updating passes the filter and invokes the worker.

Reconfigure (updating) · provisioner reconfigure(ep)

  1. R1
    Claim: UpdateItem status = provisioning with ConditionExpression #s = :updating. A ConditionalCheckFailedException means another invocation owns it: stop.
  2. R2
    Environment: GetFunctionConfiguration, merge Environment.Variables with SLIME_PROVIDER = ep.provider and SLIME_CONFIG_VERSION = ep.updatedAt, then UpdateFunctionConfiguration. The new version value forces fresh instances, which reload the SSM secrets. ResourceConflictException (update in progress) is retried every 3 s, up to 20 times.
  3. R3
    Wait until the update is done (waitUntilFunctionUpdatedV2, max 120 s).
  4. R4
    Health: GetFunctionUrlConfig for the URL, then the same healthz check as provision step 7.
  5. R5
    Result: 200 → status = ready, remove error; otherwise → status = failed with error. Any error in R2–R4 also ends in failed and returns normally.

Provisioner · teardown(ep) on status = deleting

  1. T1
    DeleteFunctionUrlConfig, then DeleteFunction.
  2. T2
    DeleteRolePolicy endpoint, then DeleteRole.
  3. T3
    DeleteLogGroup.
  4. T4
    GetParametersByPath /slime/endpoints/<id>/, then DeleteParameters.
  5. T5
    Query Liquid slime-handlers where tenantId = <id> (paged) and BatchWriteItem deletes in chunks of 25.
  6. T6
    DeleteItem of the endpoint item. USAGE#<id> items stay as billing history. Not-found errors are ignored throughout.

04Endpoint state machine

The admin writes the three states that trigger the worker; the worker writes the rest. Its own writes never match the stream filter, so it cannot loop on itself.

← scroll the diagram sideways →

Mint dashed states match the event-source filter eventName ∈ {INSERT, MODIFY}, pk prefix USER#, type = endpoint, status ∈ {pending, updating, deleting}. The admin only allows delete, a connector change or a provider change from ready or failed (ConditionExpression #s IN (:ready, :failed)); updating re-enters provisioning through reconfigure, which keeps the function, role and URL and only swaps its environment. A connector change while pending overwrites the secret without a status change, and a rename is a plain update.

06Security & IAM

The worker can create roles, so the design hinges on one rule: every role it creates must carry the boundary, and the boundary caps what any endpoint can ever do.

Principal / controlGrantsFence
Provisioner role
slime-provisioner		 read the control stream; UpdateItem/DeleteItem on slime-control; Query/BatchWriteItem on slime-handlers; SSM read/delete under /slime/endpoints/*; create/delete roles, functions, Function URLs and log groups named slime-ep-*; lambda:UpdateFunctionConfiguration on function:slime-ep-* (reconfigure); GetLayerVersion on slime-gas iam:CreateRole/PutRolePolicy only with iam:PermissionsBoundary = slime-endpoint-boundary; iam:PassRole only to lambda.amazonaws.com; every resource ARN is name-prefixed
Permissions boundary
slime-endpoint-boundary		 maximum for any endpoint: logs on /aws/lambda/slime-ep-*; Query/GetItem/PutItem/DeleteItem on handlers (the core store); UpdateItem on control; GetParametersByPath on /slime/shared and /slime/endpoints/*; X-Ray no IAM, Lambda or scan actions and no control-table deletes, so a compromised worker cannot mint a stronger role
Per-endpoint role
slime-ep-<hex>		 inline policy endpoint: handlers Query/GetItem/PutItem/DeleteItem with ForAllValues:StringEquals dynamodb:LeadingKeys = [<id>]; control UpdateItem with LeadingKeys = ["USAGE#<id>"] and dynamodb:Attributes = pk, sk, requests, generations, gasRequests, liquidRequests, crystalRequests, gasMs, liquidMs, crystalMs, tokens, gasHandlers, liquidHandlers, crystalHandlers, updatedAt; SSM /slime/shared and /slime/endpoints/<id> only; its own log group one endpoint cannot read another's Liquid partition, secrets or usage; boundary still applies
Secrets DATABASE_URL and SLIME_API_KEY as SSM SecureString under /slime/endpoints/<id>/; provider keys in /slime/shared/ never in the table, env files or span attributes; admin shows only tokenHint until "Reveal" (ownership checked first)
Stream filter event source mapping on slime-control: pk prefix USER#, type = endpoint, status ∈ {pending, updating, deleting}, batch 1, 2 retries; the worker also requires pk = USER#<owner>, sk = ENDPOINT#<endpointId> worker writes (provisioning|ready|failed) never match, so no self-trigger loop; endpoint roles may only UpdateItem the usage attributes above in USAGE#<id> (dynamodb:Attributes), so they cannot write status or forge a teardown of another endpoint
Endpoint auth public Function URL (AuthType NONE) + runtime x-api-key check on every route /healthz runs the DB safetyCheck; an unsafe customer DB ends failed, never ready
Admin sessions scrypt password hashes; HMAC-SHA256 signed cookie slime_session, HttpOnly, SameSite=Lax, 7 days endpoint reads go through the owner's pk, so users only see their own items

How to verify

  • Runtime: typecheck, tests (meter: one daily UpdateItem per flush with tier counters, latency, tokens and the gas/liquid/crystalHandlers snapshot; failing client never rejects), build produces dist/layer/slime/index.js, package.json, worker, wasm and offline handlers.
  • Provisioner: fake-client scenarios — happy path to ready, IAM propagation retry, healthz 503 → failed, lost claim issues nothing, teardown of 30 handlers in 25 + 5, pre-existing role/function tolerated, reconfigure merging the environment and retrying an in-progress update.
  • Admin, locally: npm run infra:up && npm run tables && REQUIRE_DYNAMO=1 npm test, then sign up, create an endpoint (stays pending without AWS), reveal the token, change the connector, seed daily usage and see tiers, bill and savings, check endpoint.create / dashboard.load spans in Jaeger.
  • Infra: terraform fmt/validate, tflint, trivy; the PR plan shows only additions plus a possible slime-runtime code hash change.
  • After merge (operator): put /slime/shared/ANTHROPIC_API_KEY, run the admin in AWS mode, create an offline endpoint: pending → provisioning → ready within ~60 s, healthz 200, a query bumps Requests; a provider or connector change runs updating → provisioning → ready; delete removes everything but usage.

Known limits

  • Real provisioning in AWS is verified only after merge + apply.
  • Endpoints share the account's 10 concurrent executions with slime-runtime and the landing function.
  • Existing endpoints stay on the layer version they were created with; rollout comes later.
  • Sessions are stateless and cannot be revoked before they expire.
  • The usage counter adds one DynamoDB UpdateItem (single-digit ms) to every request.

Why one Lambda per endpoint

Chosen: per-endpoint Lambdas. It is Anton's requirement, and it isolates each customer's secrets: an endpoint's role can read only its own /slime/endpoints/<id>/ parameters and its own Liquid partition. A bug or leak in one endpoint cannot expose another customer's database URL.

Cost. Every endpoint draws from the account concurrency limit of 10, shared with slime-runtime and the landing function. A shared multi-tenant Lambda would scale better per execution, but would hold every customer's secrets in one process.
